# Chitragupt: Product Discovery & Sprint Planning

This document serves as the foundation for the product discovery phase. It defines the core tenets (ontology and invariants) of the Chitragupt platform, provides essential discovery queries for stakeholders, and outlines the foundational sprints required to build the initial architecture.

---

## 1. First Principles

To build a robust agentic system, we must first establish the fundamental truths of our domain (Ontology) and the unbreakable rules of our system (Invariants). 

### 1.1 Ontology (Domain Model)
The language and entities we use to describe the Chitragupt system:

- **Source Document**: Unstructured input provided by the client (e.g., PDF, DOCX, email).
- **Knowledge Context (Chunk)**: A semantically meaningful, vector-embedded piece of a Source Document.
- **Requirement Object**: A structured, parsed unit of business need extracted from the Knowledge Context. Has subtypes: Functional, Non-Functional, Constraint, Assumption.
- **Ambiguity Incident**: A state where an Agent detects missing or conflicting information within a Requirement Object, requiring Human resolution.
- **Specification Artifact**: The structured output generated by the AI (e.g., BRD, FRD, User Story, Gap Report).
- **Agent**: A specialized AI worker within the LangGraph orchestrator that performs a specific sub-task (e.g., Planner, Validator, Clarifier).
- **Human-in-the-Loop (HITL) Gate**: A mandatory checkpoint where a human user (e.g., Business Analyst) must review, edit, and explicitly approve Agent outputs.
- **Workspace (Tenant)**: The strictly isolated environment bounding all data (Sources, Requirements, Specs) for a specific client or project.

### 1.2 System Invariants
These are non-negotiable constraints that must hold true at all times:

1. **Absolute Traceability:** Every AI-generated requirement or specification section MUST map back to one or more Source Document citations. Zero unsupported claims.
2. **Mandatory Human Approval:** No Specification Artifact can transition from "Draft" to "Approved" without explicit user authorization.
3. **Strict Tenant Isolation:** Context Chunks and Requirement Objects belonging to Tenant A must NEVER influence the retrieval or generation processes of Tenant B.
4. **Deterministic Auditing:** Every action taken by an Agent, including retrieval queries, prompt context, and output, must be immutably logged for auditability.
5. **Graceful Fallback:** If an Agent encounters an error or its confidence score falls below a defined threshold, the system MUST halt and escalate to a HITL Clarification Loop rather than hallucinating.

## 2. Stakeholder Discovery Queries

The product team must validate our assumptions and gather specific constraints from stakeholders using these queries.

### 2.1 Process & Pain Points
- *Can you walk us through the most complex requirement gathering process you've recently experienced? Where were the biggest bottlenecks?*
- *What percentage of incoming requirements are typically ambiguous, incomplete, or conflicting?*
- *How are clarification cycles currently tracked, and how much time do they consume?*

### 2.2 Quality & Output
- *What is the acceptable error rate or "hallucination tolerance" in a draft specification if the source citations are provided for easy verification?*
- *What specific sections of your current BRD/FRD templates are mandatory, and which are optional?*
- *Are there industry-specific standards or regulatory compliance requirements (e.g., HIPAA, GDPR) that must be reflected in the generated User Stories?*

### 2.3 Integration & Security
- *What existing systems (e.g., JIRA, Confluence, Azure DevOps) must the final Specifications sync with?*
- *What are the strict access control requirements within a single project? (e.g., Can PMs edit what BAs create? Can Clients view drafts?)*

## 3. Sprint Scope: Foundations (Phase 1)

These initial sprints focus exclusively on validating the first principles and establishing the core infrastructure before building the conversational UI.

### Sprint 1: Ontology, Invariants, & Infrastructure Setup
**Goal:** Establish the data models, system boundaries, and foundational Azure infrastructure.
- **Stories:**
  - Setup Azure AD B2C auth and define RBAC roles.
  - Provision Azure PostgreSQL, Blob Storage, and AI Search.
  - Define PostgreSQL schemas for `Requirement Object`, `Specification Artifact`, and `Workspace`.
  - Implement and test tenant isolation middleware.

### Sprint 2: Intake & Knowledge Representation
**Goal:** Ingest unstructured data, parse it, and represent it as structured context (First Principles: Source Document -> Knowledge Context).
- **Stories:**
  - Implement Azure Document Intelligence integration for PDF/DOCX parsing.
  - Develop semantic chunking strategy (300-500 tokens).
  - Implement embedding pipeline using `text-embedding-3-large`.
  - Build hybrid search (Dense + BM25) logic in Azure AI Search.

### Sprint 3: Core Agentic Workflows
**Goal:** Build the primary analysis logic using LangGraph (First Principles: Knowledge Context -> Requirement Object).
- **Stories:**
  - Develop the `Planner Agent` to route tasks.
  - Develop the `Requirement Understanding Agent` to extract and classify structured Requirement Objects.
  - Develop the `Specification Authoring Agent` to draft initial BRD structures.
  - Implement the fundamental RAG trace to ensure Invariant #1 (Absolute Traceability).

### Sprint 4: Verification & Human-in-the-Loop
**Goal:** Establish the trust mechanisms and approval gates (First Principles: Invariant #2, #4, #5).
- **Stories:**
  - Develop the `Validation Agent` to score confidence and detect gaps.
  - Develop the `Clarification Agent` to handle the `Ambiguity Incident` state.
  - Build the inline editing UI for HITL approval.
  - Implement the immutable audit logger for Agent traces.
