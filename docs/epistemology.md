# Epistemology: Theory of Knowledge for Chitragupt

**Phase:** Product Discovery
**Document Version:** 2.0
**Purpose:** To define how the Business Requirement Analyzer (Chitragupt) acquires, validates, trusts, and expires knowledge. In a RAG-based agentic system, epistemology is not an abstract concern — it is the operational contract between the retrieval pipeline, the LLM reasoning layer, and the human reviewer. Every design decision in chunking strategy, model selection, confidence scoring, and output tagging is a downstream consequence of the rules defined here.

---

## 1. The Hierarchy of Truth

All knowledge within Chitragupt exists within a strict authority hierarchy. When two sources conflict, this hierarchy determines precedence. A lower-tier source can **never** silently override a higher-tier one.

| Tier | Source Type | Trust Level | Override Authority |
|:---:|:---|:---|:---|
| **T1** | Human Override (explicit edit, approval, or rejection) | Absolute | Supersedes all tiers unconditionally |
| **T2** | Structured External Systems (Jira fields, DB schemas, XLSX tables) | High | Overrides unstructured text and LLM inference |
| **T3** | Primary Source Documents (PDFs, DOCX, Confluence pages, client emails) | Baseline | Overrides agentic inference |
| **T4** | Agentic Inference (LLM synthesis, deduction, inductive reasoning) | Conditional | Must be explicitly flagged; cannot stand alone |
| **T5** | Industry Standards & Regulatory Defaults (GDPR, ISO, BABOK) | Reference only | Used only to fill explicit gaps; always tagged `[INFERRED]` |

**Key Principle:** The system must be able to state, for any piece of output, which tier it originates from. Tier cannot be assumed — it must be determined by the ingestion pipeline and recorded in the chunk metadata.

## 2. Knowledge Acquisition Pathways

Chitragupt acquires knowledge through three distinct pathways. Each pathway has different epistemological properties and must be treated differently downstream.

### 2.1 Direct Ingestion (Passive Acquisition)

Knowledge arrives via uploaded documents, REST API payloads, or chat input. This is the primary pathway.

- **Trigger:** User or system uploads a file or submits a chat turn.
- **Processing:** Document Parser → NLP Extractor → Semantic Chunker → Embedding Generator → Vector Index.
- **Epistemological Status:** Resulting chunks are T3 (Primary Source) knowledge objects.
- **Limitation:** The system knows only what is explicitly contained in the ingested material. It has no epistemic access to information outside the ingested corpus unless a human explicitly provides it.

### 2.2 Retrieval-Augmented Synthesis (Active Acquisition)

Agents query the vector store to retrieve contextually relevant chunks, then synthesize new knowledge objects (requirements, constraints, assumptions) from those chunks.

- **Trigger:** An agent requires context to reason about a requirement or fill a specification section.
- **Processing:** Query Reformulation (HyDE) → Hybrid Search (Dense + BM25) → RRF Fusion → Cross-Encoder Re-ranking → Context Packing → LLM Generation.
- **Epistemological Status:** Retrieved chunks retain T3 status. The synthesized output is T4 (Agentic Inference), with confidence scored based on the quality of the grounding context.
- **Critical Constraint:** Synthesis is only epistemologically valid when grounded. A synthesis step that cannot cite at least one T3 chunk produces an Orphan (see §3.3) and must be flagged.

### 2.3 Human Elicitation (Interactive Acquisition)

Knowledge is elicited directly from a human through the clarification loop. The Clarification Agent poses targeted questions; human answers are ingested as new knowledge objects with T1 authority.

- **Trigger:** A requirement's confidence score falls below the clarification threshold (default: 70%).
- **Processing:** Clarification Agent generates questions → Human provides answers in chat → Answers are embedded and stored as a timestamped elicitation chunk.
- **Epistemological Status:** Human-provided clarifications immediately become T1 truth for the scope of the question asked. They do not retroactively change the status of previously ingested T3 documents.

## 3. Knowledge Provenance and Traceability

For any piece of knowledge to be considered "known" by the system, its origin must be structurally provable. Unknown origin is equivalent to unknown truth value.

### 3.1 The Provenance Record

Every knowledge object stored or generated by Chitragupt must carry a provenance record. This is not optional metadata — it is the epistemic identity of the object.

```json
{
  "knowledge_id": "KN-20260519-0042",
  "knowledge_type": "Requirement | Constraint | Assumption | Inference",
  "tier": "T1 | T2 | T3 | T4 | T5",
  "source_chunks": ["chunk_id_1", "chunk_id_2"],
  "source_documents": ["Payment_Gateway_V2.pdf"],
  "source_locations": ["Page 4, Section 3.2"],
  "synthesis_method": "ExplicitExtraction | DeductiveSynthesis | InductiveInference | HumanElicitation",
  "confidence_score": 0.92,
  "human_override": {
    "reviewer_id": "user-0012",
    "timestamp": "2026-05-19T10:31:00Z",
    "action": "Approved | Rejected | Edited"
  },
  "created_at": "2026-05-19T09:15:00Z",
  "embedding_model": "text-embedding-3-large-v2",
  "generation_model": "gpt-4o-2025-01",
  "session_id": "sess-abc123"
}
```

### 3.2 Citation Requirements in Output

All output artifacts (BRD, FRD, user stories, gap reports) must display visible citations.

- **Format:** `[Source: <document_name>, Pg <page>, §<section>]` or `[Elicited: BA Chat Session, <timestamp>]`
- **Inline Density:** Every discrete claim in the output requires a citation. A paragraph without a single citation is a system error, not acceptable output.
- **User Story Citations:** Citations appear in the story metadata block, not inline, to preserve narrative readability.

### 3.3 Orphan Knowledge (Hallucination Detection)

An **Orphan** is any claim generated by the LLM that cannot be mapped to a stored chunk in the current tenant's project vector namespace.

- **Detection:** The Validation Agent runs a post-generation citation audit. Any claim with no traceable `source_chunks` reference is flagged as an Orphan.
- **Disposition:** Orphans are never silently included in output. They are either (a) pruned entirely, or (b) retained and tagged `[UNVERIFIED - SOURCE NOT FOUND]` for human review, depending on project configuration.
- **Root Cause Signal:** Orphans indicate context window truncation, embedding failure, or LLM confabulation. The Validation Agent logs orphan events to the observability layer (LangSmith) for engineering investigation.

## 4. Degrees of Certainty and Confidence Scoring

The system must never present all generated text with equal epistemic weight. The confidence score is the numerical expression of how well a knowledge claim is grounded in retrieved evidence.

### 4.1 Confidence Levels and Synthesis Methods

| Synthesis Method | Confidence Band | Meaning | Output Tag |
|:---|:---|:---|:---|
| **Explicit Extraction** | 0.90 – 1.00 | Direct quote or unambiguous statement from a T2/T3 source | *(no tag — default clean output)* |
| **Deductive Synthesis** | 0.75 – 0.89 | Two or more explicit T3 facts logically combined | *(no tag if above `CONFIDENCE_TAG_THRESHOLD`)* |
| **Deductive Synthesis (weak support)** | 0.60 – 0.74 | Logical conclusion from weak or single-source evidence | `[VERIFY]` |
| **Inductive Inference** | 0.40 – 0.59 | Pattern-based inference; industry standard applied | `[INFERRED - REQUIRES VALIDATION]` |
| **Speculative Generation** | 0.00 – 0.39 | Minimal grounding; high orphan risk | `[SPECULATIVE - DO NOT USE]` |

### 4.2 Confidence Calculation Rules

Confidence scores are **not** raw LLM logit probabilities. They are composite scores computed by the Validation Agent:

1. **Retrieval Relevance Score (40% weight):** Average cross-encoder re-ranker score of the top-K chunks used as context.
2. **Source Tier Multiplier:** T2 sources multiply base score by 1.0; T3 by 0.85; T4 by 0.60; T5 by 0.40.
3. **Citation Coverage (30% weight):** Ratio of claimed facts to cited facts in the output passage.
4. **Consistency Check (30% weight):** Whether the claim is contradicted by any other retrieved chunk. A detected contradiction forces the score to a maximum of 0.50 regardless of other factors.

### 4.3 Threshold Configuration

Confidence thresholds are configurable per tenant but have enforced global minimums:

| Threshold Name | Default | Purpose |
|:---|:---|:---|
| `CLARIFICATION_THRESHOLD` | 0.70 | Triggers Clarification Agent to ask human a question |
| `CONFIDENCE_TAG_THRESHOLD` | 0.85 | Below this, outputs are visually tagged `[VERIFY]` |
| `INCLUSION_THRESHOLD` | 0.40 | Below this, outputs are suppressed from the spec and appear only in the Gap Report |
| `ORPHAN_CITATION_THRESHOLD` | 0.95 coverage | Below this, a passage is submitted for orphan analysis |

## 5. RAG-Specific Epistemology

The RAG pipeline introduces unique epistemological properties that must be understood and governed.

### 5.1 Embedding as Semantic Approximation

A vector embedding is not a precise knowledge representation. It is a dimensionality reduction of semantic meaning.

- **Implication:** High cosine similarity between a query vector and a chunk vector indicates *semantic relatedness*, not *factual equivalence*. A retrieved chunk may be topically related but contextually irrelevant.
- **Rule:** Embedding similarity alone is insufficient to establish grounding. The Cross-Encoder Re-ranker must run over all top-K candidates before any chunk is used as supporting evidence. A chunk that passes dense retrieval but fails re-ranking is not considered supporting evidence and must not be cited.

### 5.2 Chunking as Knowledge Fragmentation

Semantic chunking divides documents into 300–500 token segments. This engineering compromise creates epistemological risk.

- **Risk:** A key constraint may span two chunks and be split at the boundary, making neither chunk individually sufficient to convey the full meaning.
- **Mitigation:** 10% token overlap between adjacent chunks reduces split-point information loss. The Retrieval Agent fetches parent document context (the ±1 surrounding chunks) whenever a retrieved chunk's relevance score is below 0.80.
- **Rule:** A single chunk is never treated as the *complete* knowledge of a section. The `parent_document` and `section_id` metadata must be checked to determine whether sibling chunks should be co-retrieved.

### 5.3 Query Formulation Epistemology (HyDE)

Hypothetical Document Embedding (HyDE) pre-expands a query by asking the LLM to generate a hypothetical ideal answer before encoding it as a query vector.

- **Risk:** The hypothetical answer is pure T4 inference and may contain false premises that bias retrieval toward confirming those premises — a form of retrieval-level circular reasoning.
- **Rule:** The HyDE expansion is used only for query vector construction and is discarded entirely after the dense search step. It must never appear in output citations.

### 5.4 Retrieval Scope Isolation

The epistemological validity of a retrieved chunk is contingent on correct scope. A chunk from the wrong project, tenant, or document version corrupts the current session's knowledge base.

- **Rule:** Every retrieval query must include mandatory metadata filters: `tenant_id`, `project_id`, and optionally `document_version`. These filters are enforced at the vector store query level, not post-retrieval. Bypassing these filters is a system invariant violation (see invariants.md §2).

### 5.5 Hybrid Search Epistemology

Chitragupt uses both dense (semantic) and sparse (BM25 keyword) retrieval, fused via Reciprocal Rank Fusion (RRF). Each has distinct epistemological properties:

- **Dense Search** excels at semantic similarity but may miss exact domain terms (e.g., "ISO 27001 Annex A").
- **BM25 Keyword Search** excels at exact term matching but misses paraphrases and synonyms.
- **Rule:** Neither retrieval method alone is epistemologically sufficient for a business-critical retrieval task. Both must be run and their results fused. A configuration that disables either leg of hybrid search is not permitted in production.

### 5.6 Knowledge Staleness

Ingested knowledge has a temporal dimension. A document ingested 6 months ago may not reflect the current state of client requirements.

- **Rule:** Every chunk carries a `last_ingested_at` timestamp. The Validation Agent must surface the `last_ingested_at` date when generating any specification section. If any supporting chunk is older than the project's `staleness_threshold` (default: 90 days), the section is flagged `[SOURCE MAY BE OUTDATED - VERIFY WITH CLIENT]`.
- **Re-ingestion:** Staleness warnings do not trigger automatic re-ingestion (see Manual Trigger Invariant). They only produce a human-visible warning.

## 6. AI Model Selection Epistemology

Different AI models have fundamentally different epistemological properties. Model selection determines the quality, consistency, and reliability of the knowledge the system can produce — it is not purely a performance or cost decision.

### 6.1 Model Roles and Epistemic Boundaries

| Task | Assigned Model | Epistemic Rationale |
|:---|:---|:---|
| Requirement synthesis, BRD/FRD authoring, validation | GPT-4o (primary) / Claude Sonnet 4.6 (fallback) | Complex multi-step reasoning over long context; strong instruction-following for structured output |
| Query reformulation (HyDE expansion) | GPT-4o-mini | Lower stakes; output discarded post-retrieval; cost-optimized for high-frequency calls |
| Confidence scoring | Deterministic formula + cross-encoder model | No generative LLM in confidence calculation; avoids LLM self-assessment bias |
| Clarification question generation | GPT-4o | Questions are client-facing; quality and specificity are critical |
| Gap analysis | GPT-4o | Must reason rigorously about the absence of information; requires the strongest available model |
| Document embedding | text-embedding-3-large (primary) / Cohere Embed v3 (fallback) | Highest semantic fidelity; model must be pinned to a specific version for index consistency |
| Re-ranking | FlashRank cross-encoder / Cohere Rerank (fallback) | Precision-critical step that determines final evidence selection before LLM context packing |

### 6.2 Model Pinning Principle

The embedding model used at ingestion time **must** be the same model version used at query time. Changing the embedding model invalidates the entire vector index for that tenant.

- **Rule:** The `embedding_model_version` used to generate each chunk's vector is stored in chunk metadata. At query time, the system verifies the query embedding was generated by the same model version. A mismatch triggers query rejection and a re-ingestion alert.

### 6.3 Model Fallback Epistemology

When the primary LLM is unavailable and a fallback model is used:

- **Rule:** The `generation_model` field in the Provenance Record must reflect the actual model used, not the intended primary.
- **Rule:** If the fallback model produces output that differs materially in reasoning quality (e.g., a significantly smaller model is used due to an outage), the output must carry `[GENERATED WITH FALLBACK MODEL - REVIEW ADVISED]`.
- **Rule:** Embedding model fallbacks always require full re-indexing before production use. An embedding generated by a different model cannot coexist in the same index namespace.

### 6.4 Temperature and Determinism

LLM temperature settings are an epistemological variable. Higher temperature increases output diversity at the cost of grounding consistency.

- **Rule:** All specification authoring and requirement synthesis tasks must use **temperature ≤ 0.2**. This prioritizes faithfulness to the retrieved context over stylistic variation.
- **Rule:** Clarification question generation may use **temperature ≤ 0.4** to allow natural question phrasing variation without compromising specificity.
- **Rule:** Any output generated at temperature > 0.5 must be tagged `[ILLUSTRATIVE - NOT GROUNDED]` and cannot be included in the formal specification without human promotion to approved status.

## 7. Handling Contradictions

Contradiction is an epistemologically significant event. The system's response to it defines its intellectual integrity.

### 7.1 Types of Contradiction

| Type | Definition | Example |
|:---|:---|:---|
| **Direct Contradiction** | Two sources make mutually exclusive factual claims about the same subject | Jira says "Daily Sync"; PDF says "Real-time Sync" |
| **Scope Contradiction** | Two sources agree on a fact but disagree on its scope or applicability | Email says "mobile only"; DOCX says "all platforms" |
| **Temporal Contradiction** | An older source states something a newer source supersedes without explicit reference | V1 PDF: "3 user roles"; V2 PDF: "5 user roles" |
| **Implied Contradiction** | No explicit conflict, but logical deduction reveals incompatibility | Budget constraint implies feature A is not feasible, but feature A is listed as mandatory |

### 7.2 Contradiction Detection

The Validation Agent runs contradiction detection across all retrieved chunks before any specification section is authored:

- **Direct and Scope:** Detected by comparing claim triples (subject, predicate, object) extracted from chunks that share the same subject and predicate but have different objects.
- **Temporal:** Detected by comparing `created_at` timestamps on conflicting chunks from the same source document family (matched by title prefix or document lineage metadata).
- **Implied:** Detected by the consistency checker running structured logical inference over the full requirement set.

### 7.3 Conflict Resolution Authority

The system **does not** possess the epistemological authority to resolve any contradiction type. This is a categorical rule.

- When a contradiction is detected, a **Conflict Flag** is created as a first-class knowledge object with its own ID and provenance record.
- The dependent specification section enters a **BLOCKED** state. The Authoring Agent produces a placeholder: `[CONFLICT: This section cannot be authored until Conflict Flag <ID> is resolved by a reviewer. See Gap Report.]`
- The Conflict Flag is prominently surfaced in the Gap Analysis Report with verbatim conflicting quotes from both sources.
- **Only a T1 human action** unblocks a Conflict Flag and allows authoring of the dependent section.

### 7.4 Temporal Contradiction Heuristic (Limited Exception)

For temporal contradictions where the newer document is unambiguously a revision of the older one (identified by shared title with a version suffix), the system **may** apply a soft preference for the newer document, but only when:

- The confidence delta between the two sources is less than 0.10.
- The preference is logged visibly as `[Superseded by: <newer_document_name>]`.
- This behavior is configurable and **disabled by default** for regulated industry projects.

## 8. Session Knowledge vs. Persistent Knowledge

### 8.1 Session Knowledge (Ephemeral)

- Exists only within a single agent invocation or conversation turn.
- Includes: conversation buffer, retrieved chunk cache, intermediate agent reasoning traces, active clarification question states.
- **Rule:** Session knowledge must never be written to the persistent vector store or structured database.
- **Rule:** Session knowledge is destroyed when the session ends. Nothing survives unless explicitly promoted to a persistent knowledge object via a human approval action.

### 8.2 Persistent Knowledge (Durable)

- Exists across sessions and is retrievable in future conversations.
- Includes: ingested document chunks (vector store), human-approved requirement objects (PostgreSQL), audit logs.
- **Rule:** Only T1-approved or T3-ingested objects may be written to the persistent store. T4 objects are persisted only after receiving a T1 human approval action, at which point their tier is upgraded to T1-approved.

### 8.3 Cross-Project Knowledge Usage

Knowledge from past projects is valuable but carries epistemic risk when applied to a new project.

- **Rule:** Cross-project retrieval is enabled only when the user explicitly requests it (e.g., "Find similar requirements from past projects"). It is never on by default.
- **Rule:** Any content sourced from a different project's knowledge base must be tagged `[CROSS-PROJECT REFERENCE: <project_name>]` and cannot be included in final output without explicit human approval.

## 9. Human-in-the-Loop as the Epistemic Apex

Human oversight is not a fallback mechanism — it is the highest-authority epistemic actor in the system.

### 9.1 The Human Override Effect

When a human reviewer edits, approves, or rejects an LLM-generated output:

- The action is immediately recorded as a T1 knowledge event with timestamp and reviewer ID.
- The T1 record supersedes the original T4 output in all future retrieval queries for that section.
- **Re-generation Lock:** Subsequent re-generation requests for the same section must load the human edit as a hard constraint in the LLM system prompt. The T4 original is archived with status `SUPERSEDED_BY_HUMAN` and remains in the audit trail; it is never deleted.

### 9.2 Approval as Epistemic Promotion

- A Draft requirement (T4) → Human Approval → becomes a T1-approved requirement, safe to be referenced by downstream agents as a reliable foundation.
- An `[INFERRED]`-tagged assumption → Human confirmation → the tag is removed, confidence score is set to 1.0, and the provenance record is updated with the reviewer's ID.

### 9.3 Rejection as Negative Knowledge

Human rejection of an LLM output is a negative knowledge signal, not a neutral event.

- Rejected objects are stored with status `REJECTED` and the reason (if provided).
- The Validation Agent checks all new outputs against the rejected object catalog. If a newly generated requirement has cosine similarity > 0.90 to a previously rejected one, it is automatically flagged for human review rather than silently included in the draft.

## 10. Knowledge Lifecycle and Governance

### 10.1 Knowledge Object States

```
[Ingested / Generated]
        ↓
     [Draft]  ← T4 synthesized output
        ↓
   [In Review] ← human is evaluating
        ↓              ↓
  [Approved]       [Rejected]
  (T1 ground        (negative
    truth)           evidence)
        ↓
  [Archived] ← superseded by a newer approved version
```

| State | Epistemological Meaning |
|:---|:---|
| **Ingested** | Raw chunk in vector store; T3 status; not yet synthesized |
| **Draft** | T4 synthesized output; confidence-tagged; not yet human-reviewed |
| **In Review** | Actively being evaluated by a human reviewer |
| **Approved** | T1 status; human-validated ground truth; safe for downstream use |
| **Rejected** | Permanently excluded; preserved as negative evidence in audit trail |
| **Archived** | Older version superseded by a newer approved version; retained for audit |

### 10.2 Knowledge Expiry and Staleness Policy

| Knowledge Type | Staleness Threshold | Action on Expiry |
|:---|:---|:---|
| Ingested document chunks | 90 days (configurable per tenant) | Flag generated outputs with `[SOURCE MAY BE OUTDATED]`; notify project owner |
| Human-approved requirements | No automatic expiry | Valid until explicitly revised or rejected by a human |
| Cross-project reference knowledge | 180 days (configurable) | Require re-approval before reuse in new projects |
| Clarification elicitations | Project lifetime | Expire with project archival |

### 10.3 Audit Trail as Epistemic Record

The audit log is not merely a security artifact — it is the definitive historical record of how each piece of output came to exist.

- Every state transition for every knowledge object (Ingested → Draft → Approved, etc.) is logged immutably.
- Every agent invocation is logged with its inputs, outputs, and model parameters.
- The audit trail must be sufficient to reconstruct the epistemic lineage of any output from ingestion to approval without reference to any other system.
